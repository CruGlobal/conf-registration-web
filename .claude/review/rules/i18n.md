# Internationalization (i18n) Focus Areas

AngularJS screens use `angular-gettext`. Strings are marked in templates and JS, and `yarn angular-gettext-extract` collects them into `languages/ert.pot`. The app does not load any translations at runtime today (there is no `gettextCatalog.setCurrentLanguage` or `setStrings` call), so a missed string will not look broken in review. Flag it anyway: the team's own PR-review prompt lists "Missing internationalization for user-facing strings". Keep these findings low severity unless a whole new screen ships with nothing marked.

**Templates** (`app/**/*.html`)

- Mark text with the `translate` attribute (`<span translate>Card Number</span>`) or element (`<translate>My Dashboard</translate>`).
- Mark attributes with the filter: `placeholder="{{'City' | translate}}"`, `aria-label="{{ 'Sort by Code' | translate }}"`, `uib-popover="{{'...' | translate}}"`, and the same for `uib-tooltip` and `title`.
- Look for: new visible text, `placeholder`, `title`, `aria-label`, `alt`, `<legend>`, and `<option>` labels with no marking. Existing misses (`placeholder="Event name"` in `landing.html`, the month names and the `Credit Card` legend in `paymentMethods/creditCard.html`, "Sign in with Facebook" in `loginDialog.html`) are not a model. Don't flag them unless the PR touches those lines.
- `{{ }}` inside a translated element becomes part of the msgid (`<h2 translate>{{$ctrl.getMinistryName()}} Promotions</h2>`). Keep it to one simple value. Look for: logic inside, like `<td translate>{{payment.reported?"Yes":"No"}}</td>`, which makes a msgid nobody can translate. Translate each word on its own instead.
- Don't split one sentence into pieces (`<translate>No events found matching</translate> "{{searchComplete}}"`). Other languages may need a different word order. Use one string with a placeholder.

**JavaScript**

- Messages built in JS use `gettextCatalog.getString('...')`, with values passed as the second argument: `gettextCatalog.getString('You are paying more than the total due of {{remainingBalance}} to register for this event.', { remainingBalance })` (`services/payment.js`, `directives/payment/payment.js`).
- The string must be a literal so the extractor can find it. Look for: `getString(variable)`, template literals, or `+` joins inside `getString`.
- Route titles in `app.config.js` use the injected `gettext('...')` marker, which only marks the string; `index.ejs` translates it with `pageTitle | translate`. New routes need `title: gettext('...')`.
- Look for: new user-facing strings pushed into error lists, `modalMessage` titles and messages, `notify.message` banners, or `$rootScope.loadingMsg` with no `getString`. Plenty of old code does this (for example `'Please enter your card billing details.'` in `directives/payment/payment.js`). Only flag new or changed lines.

**What the extractor can't see**

- The extract script only scans `./app/**/*.@(js|html)` and skips `*.spec.js`. Strings in `.ts`, `.tsx`, and `app/index.ejs` are never extracted, and no `.ts` file uses `gettextCatalog` today. Look for: user-facing text moved from a `.js` or `.html` file into `.ts` (for example the modal text in `globalPromotionService.ts`). It drops out of translation. Keep text in the template where you can.
- React components render plain English, and `package.json` has no React i18n library. The `translate="yes"` attributes in `ExportModal.tsx` do nothing, because Angular never compiles React output. Look for: new `translate` attributes in JSX, or a PR that claims React text is translated. If a new registrant-facing screen is built in React, raise translation as a question.
- `languages/ert.pot` is not rebuilt in normal PRs, and its `#:` lines still point at the old `app/views/` paths. Don't ask for a `.pot` update. If a PR does run `yarn angular-gettext-extract`, check that the diff holds only path moves and the new msgids.

**Formats**

- Money: the `localizedCurrency` filter uses `$locale.id` and the event's `currency.currencyCode`. Look for: hand-built currency strings.
- Dates: `evtDateFormat` (`moment.tz(date, zone)`, default format `'MMM D, YYYY h:mm a z'`) and `dateRangeFormat`. Look for: new hard-coded English date formats or month names in JS.
- Addresses: the `addressConstants` patterns in `services/constants.js` are meant to work for any country (see the `zip` comment), and `validateRegistrant` uses `country-region-data` for states. Look for: US-only checks (5-digit ZIP, US state lists) applied to every country.
- Changing the English text of an existing `translate` string creates a new msgid. That is fine when the wording should change. Avoid it for style-only edits.

**Checklist**

- [ ] New template text, placeholders, titles, and aria-labels marked with `translate`
- [ ] New JS messages use `gettextCatalog.getString` with literal strings and `{{name}}` placeholders
- [ ] New routes have `title: gettext('...')`
- [ ] No logic inside translated interpolation; no sentences split into pieces
- [ ] Text that needs translation lives in `.js` or `.html`, not in `.ts`, `.tsx`, or JSX

## Mined from PR history

- Every new user-facing string in a template is marked, attributes included: `aria-label`, `placeholder`, `title`, and `uib-popover` use `{{'Text' | translate}}`, and sr-only legends and spans use `translate`. Keep `fa` icon elements empty and put text in a sibling `<span translate>`, since the icon font garbles text inside it.
  <!-- evidence: PR #876, #880, #888, #891, #896, #902, #911, #913, #939, #945, #969 -->
- One sentence is one translatable string with `{{ }}` values. Flag sentences split into pieces (`<translate>full</translate> ... <translate>of</translate> ...` in `eventRegistrations.html`) and a sentence broken around a link (the "ERT 101" line in `help.html`).
  <!-- evidence: PR #785, #938, #939, #940, #949 -->
- Strings built in JS (error lists, `modalMessage` text, `$scope.notify` HTML, the auth error text in `app_enforceAuth.js`) go through `gettextCatalog.getString` where they are defined. A `translate` on the template can't see dynamic values. Check new strings for typos too ("plesase" from #769 is still live).
  <!-- evidence: PR #765, #769, #998, #999, #1001 -->
- Don't put a ternary inside a translated expression (`{{ cond ? 'ZIP' : 'Postal Code' | translate }}`, or `translate` on an element holding `{{ cond ? 'Active' : 'Inactive' }}`). The extractor misses both strings. Use two `ng-if` elements that each hold one literal.
  <!-- evidence: PR #779, #925, #930 -->
- `translate` attributes in `.tsx` files do nothing, and the extractor only scans `app/**/*.@(js|html)`. Flag new `translate` attributes in JSX, and treat new React text as untranslated unless the PR adds a real path (for example `gettextCatalog` passed in as a react2angular injectable).
  <!-- evidence: PR #782, #799, #804, #825 -->
- Open team decision: some reviewers asked PRs to regenerate `languages/ert.pot`, but in practice it has not been rebuilt since about #836. Until the team decides, don't block on a missing `.pot` update; do check that each new string can be extracted (plain literal text, not built from expressions).
  <!-- evidence: PR #812, #825, #830, #837, #838, #922, #928, #930 -->
